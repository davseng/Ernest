## Inspect the clone; do not replay historical migrations

Migration `022_boat_devices.sql` declares `boat_devices.asset_id uuid`; migration `001` declares `assets.id text`. Replaying that CREATE against a fresh text-key schema fails with SQLSTATE 42804. This does **not** establish that a production clone is incompatible.

Possible clone states:

| Observed schema | Decision |
| --- | --- |
| `assets.id text`, existing `boat_devices.asset_id text`, valid FK to `assets(id)` | Already compatible; preserve it. Do not replay or rewrite 022. |
| `assets.id text`, `boat_devices` absent | Boat-device functionality is not initialized. It is not a prerequisite for 025 or the web v0.11 acceptance flows. Leave it absent; keep boat integration out of this rollout. |
| Existing mismatched type/missing FK or another asset key type | Stop that subsystem for schema review. Do not cast identifiers or rebuild tables. 025 requires text asset IDs. |
| 022 recorded in `schema_migrations` but actual schema differs from its file | Record the discrepancy. Actual types/constraints govern compatibility; do not falsify history or rerun the file to make it match. |

The supported inspector reads only catalog metadata and migration names, within a read-only transaction. It never prints database URLs, credentials, vessel rows or integration tokens. It also checks the existing tables required for 025 and reports any pre-existing 025 drift.

From the repository root, with `V011_DATABASE_URL` injected securely:

```bash
export V011_NEON_BRANCH=ernest-v011-test
export V011_EXPECTED_DB_HOST='<direct endpoint hostname copied from ernest-v011-test in Neon>'
node scripts/v011/database.mjs inspect
```

Replace the angle-bracket placeholder with the real hostname. Map that exact endpoint to the branch in Neon **before** running either mode. The program cannot infer the human branch name from SQL or prove that a user-supplied hostname belongs to it. It refuses ambient `DATABASE_URL`, a different hostname, a pooled endpoint, and any branch label other than `ernest-v011-test`. It uses TLS certificate verification.

If using Neon SQL editor instead, select the isolated branch and database explicitly, then run these **read-only** statements. The server database name or IP alone does not prove Neon branch identity; selection and endpoint mapping must come from Neon.

```sql
BEGIN READ ONLY;
SELECT current_database(), current_user;
SELECT c.relname AS table_name, a.attname AS column_name,
       pg_catalog.format_type(a.atttypid,a.atttypmod) AS data_type
FROM pg_attribute a
JOIN pg_class c ON c.oid=a.attrelid
JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE n.nspname='public' AND a.attnum>0 AND NOT a.attisdropped
  AND c.relname IN ('assets','users','boat_devices','documents','document_pages',
                   'procedures','procedure_steps','document_findings','external_connections',
                   'owner_knowledge','procedure_revisions','document_processing_status',
                   'document_visual_pages','document_page_embeddings')
ORDER BY c.relname,a.attnum;
SELECT conname, conrelid::regclass, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid=to_regclass('public.boat_devices');
SELECT to_regclass('public.schema_migrations') AS migration_ledger;
COMMIT;
```

Only if the ledger exists, separately query its names for 022 and 025. Do not create entries for historical migrations merely because a table exists. If prerequisites are missing, stop and inspect the cloned schema; do not invoke the general migration runner.

## Apply exactly 025, once schema and endpoint are verified

The owner has authorized preparation for the isolated branch. No live DDL has been executed here because the connection is unavailable. Do not put this command in Vercel build/start commands or the general environment install script.

1. Confirm Neon branch/endpoint mapping and the latest read-only inspector result. Resolve `prerequisiteIssues` and `existing025Drift`; do not proceed with unexpected asset types or ledger/schema drift.

3. Run from the repository root, using the same secure URL and pinned host:

```bash
node scripts/v011/database.mjs apply-025
node scripts/v011/database.mjs inspect
```

`apply-025` executes **only** `migrations/025_competence_memory_action.sql`. In one transaction it sets a 5-second lock timeout and 120-second statement timeout, takes a migration advisory lock, checks prerequisites, applies additive DDL, checks resulting object types/index presence, and records only 025 in `schema_migrations`. Existing matching recorded 025 is a no-op; inconsistent recorded state fails closed. A DDL or postflight failure rolls back the DDL and ledger write together. A timeout means retry after diagnosis or an isolated maintenance window; never disable checks or raise limits blindly.

025 creates knowledge/history/processing/visual/embedding tables and search indexes, and adds `procedures.revision` with default 1. It does not seed, delete documents, replace procedures, rewrite IDs, clear integrations, or change 022. Normal index creation can briefly lock tables, hence the bounded lock wait. No pgvector extension is required.

For the Neon editor alternative: after the same inspection, open a single transaction, set the two timeouts and `search_path=public,pg_catalog`, acquire `pg_advisory_xact_lock(hashtext('ernest-v011-025'))`, paste the **unchanged complete contents** of migration 025, and inspect the results before committing. Record only `025_competence_memory_action.sql` in the existing ledger (or create the standard ledger if genuinely absent). Use `ON CONFLICT(name) DO NOTHING` only after verifying the existing recorded schema is compatible. Roll back on any error. The guarded Node runner is preferred because it enforces pre/postflight checks consistently.

Do **not** run `npm run db:migrate` or `npm run db:seed` for this rollout. A clone can already contain manually applied compatible schema, regardless of its historical ledger.
